## TASK 9B : String-Based Application Logic

### 1. Circuit Diagram

The experiment implements a UART command interface in which lines typed in a PC terminal are received over USART2 and used to switch the onboard user LED on PC13, with a status reply sent back to the terminal.

- **Development Board:** STM32 Blue Pill
- **Microcontroller IC:** STM32F103C8T6 (ARM Cortex-M3), clocked from the 8 MHz crystal with PLL ×9 for a 72 MHz system clock
- **UART Peripheral:** USART2, configured for 9600 baud, 8 data bits, no parity, 1 stop bit, no hardware flow control
- **UART Pins:** PA2 (USART2_TX) to the RXD pin of the USB-to-TTL adapter; PA3 (USART2_RX) to the TXD pin of the adapter, so the two are crossed
- **Output Pin:** PC13, the onboard LED, which is active LOW — the LED is ON when the pin is driven LOW
- **Peripheral:** USB-to-TTL adapter (CP2102 / CH340 / FT232RL) connected to the PC, with PuTTY opened at 9600 8-N-1
- **Power Supply:** the board is powered from the 3.3 V pin of the ST-Link V2; the 3V3 pin of the adapter is left unconnected
- **Ground:** common GND shared between the STM32, the ST-Link V2 and the USB-to-TTL adapter
- **Programming and Debug:** ST-Link V2 on the 4-pin SWD header — 3V3, SWDIO, SWCLK and GND

### 2. Core Logic / Pseudocode / Code Base

**Working Principle:**

PC13 is configured in `MX_GPIO_Init()` as a push-pull output with no pull resistor and low speed, and it is driven LOW at start-up so the onboard LED begins in the ON state, since the LED on the Blue Pill is wired active LOW. USART2 is set up in the same way as in Task 9A, at 9600 baud 8-N-1 with both transmit and receive enabled.

Reception is interrupt-driven and one byte at a time. `HAL_UART_Receive_IT()` arms the receiver, and every byte arriving from PuTTY raises the USART2 interrupt, which the HAL passes to `HAL_UART_RxCpltCallback()`. The callback appends the byte to `rxBuffer`, a 50-character array indexed by `rxIndex`, and re-arms the interrupt with `HAL_UART_Receive_IT()` so that the next character is captured.

When the received character is a carriage return (`'\r'`) or a line feed (`'\n'`) and the buffer is not empty, the buffer is terminated with `'\0'` and the completed line is passed to `Process_Command()`; the index is then reset to zero so the next command starts at the beginning of the buffer. Treating both delimiters as the end of a line means the same commands work whether PuTTY is set to send CR, LF or both.

`Process_Command()` matches the line against the accepted commands with `strstr()`. `"LED ON"` writes `GPIO_PIN_RESET` to PC13, which lights the active-LOW LED, and replies `"LED turned ON"`; `"LED OFF"` writes `GPIO_PIN_SET`, which extinguishes it, and replies `"LED turned OFF"`; `"LED TOGGLE"` flips the pin with `HAL_GPIO_TogglePin()` and replies `"LED toggled"`. Any other line is answered with `"Unknown command"`, and every reply is sent back over the same USART2 with `HAL_UART_Transmit()`.

**Pseudocode:**

1. Initialise the HAL library and configure the system clock with HSE and PLL ×9.
2. Enable the GPIOC clock and configure PC13 as a push-pull output, driving it LOW so the active-LOW LED starts ON.
3. Initialise USART2 at 9600 baud, 8 data bits, 1 stop bit and no parity.
4. Declare the receive byte `rxData`, the buffer `rxBuffer[50]` and the index `rxIndex`.
5. Arm the first receive with `HAL_UART_Receive_IT(&huart2, &rxData, 1)`.
6. Enter the infinite `while (1)` loop, which waits for interrupts.
7. On each received byte, enter `HAL_UART_RxCpltCallback()`.
8. If the byte is `'\r'` or `'\n'` and `rxIndex` is greater than zero, terminate the buffer and call `Process_Command(rxBuffer)`, then reset `rxIndex` to zero.
9. Otherwise, if `rxIndex` is below 49, store the byte in `rxBuffer` and increment the index.
10. In `Process_Command()`, compare the line with `strstr()` against `"LED ON"`, `"LED OFF"` and `"LED TOGGLE"`.
11. For `"LED ON"`, write PC13 LOW and transmit `"LED turned ON"`.
12. For `"LED OFF"`, write PC13 HIGH and transmit `"LED turned OFF"`.
13. For `"LED TOGGLE"`, toggle PC13 and transmit `"LED toggled"`.
14. For anything else, transmit `"Unknown command"`.
15. Re-arm the receive interrupt with `HAL_UART_Receive_IT()` before leaving the callback.

**Code Base:**

The program is written in Embedded C, with the peripherals generated by STM32CubeMX and the project built in Keil MDK against the STM32 HAL library, including `<string.h>` for the string matching. The `.ioc` file and the generated `Core/` and `Drivers/` folders are kept with the project.

- `MX_GPIO_Init()` enables the GPIOC clock, drives PC13 LOW at start-up and configures it as `GPIO_MODE_OUTPUT_PP` with no pull and low speed.
- `MX_USART2_UART_Init()` sets `huart2` to 9600 baud, 8 data bits, 1 stop bit, no parity and transmit/receive mode.
- `HAL_UART_Receive_IT()` and `HAL_UART_RxCpltCallback()` provide the interrupt-driven reception, the line buffer and the re-arming of the receiver.
- `Process_Command()` uses `strstr()` to recognise the three commands and drives PC13 with `HAL_GPIO_WritePin()` or `HAL_GPIO_TogglePin()`.
- `HAL_UART_Transmit()` sends the acknowledgement strings back to the terminal from inside the same command handler.

### 3. Inference

Lines typed into PuTTY were received over USART2 and echoed back as status messages — `LED turned ON`, `LED turned OFF`, `LED toggled` and `Unknown command` — without the main loop doing any work, because the reception was handled entirely in the UART interrupt callback.

The onboard PC13 LED responded correctly for an active-LOW output, lighting when the pin was driven LOW by `"LED ON"` and going dark on `"LED OFF"`, while `"LED TOGGLE"` changed its state on every entry.

The experiment demonstrates interrupt-driven serial reception on the STM32, assembling a string from individual received bytes, matching that string against a command set, and turning a typed command into a physical output on the board with a confirmation sent back to the terminal.
