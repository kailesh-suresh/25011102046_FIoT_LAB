The idea, in plain words

Two thermometers walk into a room

One is ours: a small chip on a breadboard that measures the air right next to it. The other is the official weather service for the same district. They never agree exactly — and the interesting part is why they disagree.

Most student weather projects stop at showing a number on a screen. That answers “what is it right now”, which a ₹500 gadget also answers. This project asks a harder and more useful question: when two independent measurements of the same sky disagree, which one should you trust, and what does the difference actually mean?

The answer turns out to be different for each quantity. Pressure agrees to within three thousandths of a percent once both are corrected to the same reference. Temperature and humidity never will, because they are not measuring the same thing at all — one is indoor air beside a warm circuit board, the other is air two metres above open ground. Saying that clearly is the whole point of the system.

A reading is not information until you know what it is allowed to disagree with.
The chain

Five hops, from a silicon die to a decision

Everything below is one continuous path. Each hop exists because the previous one cannot do the next job: the sensor cannot speak, the microcontroller cannot join Wi-Fi, the Wi-Fi module cannot reason.

Hop 1 — sense

The chip

A BME280 measures temperature, humidity and pressure, and hands the numbers over a two-wire bus. It measures well and communicates badly.

Hop 2 — think

The board

An STM32F401RE reads the chip, formats the answer as JSON, and serves it as a web reply. It has no idea what the internet is.

Hop 3 — speak

The radio

An ESP8266 holds the Wi-Fi link and the TCP socket. It forwards the browser’s request to the board and the board’s answer back.

Hop 4 — listen

Node-RED

A flow engine polls the board every five seconds, parses the JSON, and pushes each number to the right widget.

Hop 5 — decide

The verdict

Two sources meet in one function node, get compared honestly, and become a ranked list of things you could actually do this morning.

Step 01
01sensing

Measuring the air

The BME280 sits on the I2C bus at address 0x76 (falling back to 0x77 if the module is strapped that way). Three registers give three physical quantities, and each one means something a person can feel:

QuantityUnitWhat a person actually feels
Temperature°CWhether you need a jacket, and whether the sensor is sitting next to something warm
Humidity%RHWhether sweat dries, and whether dew will be on the grass at dawn
PressurehPaNothing directly — it is a forecast. Falling pressure means weather is on the way
main.c — reading and scalingI2C1
/* The Bosch driver changed its output units between releases. Old builds
   return hundredths of a degree; newer builds return degrees as doubles.
   Guessing wrong gives 0.30 °C and 0.07 %RH — the right numbers, divided
   by 100 and 1024 a second time. sizeof() settles it at compile time. */
if (sizeof(((struct bme280_data *)0)->temperature) == sizeof(double)) {
    temperature  = (float)data.temperature;          /* already °C  */
    humidity     = (float)data.humidity;             /* already %RH */
    pressure_hpa = (float)data.pressure / 100.0f;  /* Pa → hPa    */
} else {
    temperature  = (float)data.temperature / 100.0f;
    humidity     = (float)data.humidity / 1024.0f;
    pressure_hpa = (float)data.pressure / 100.0f;
}
This cost us a night. The sensor was reporting 0.30 °C and 0.07 %RH for hours while the pressure looked perfect — because pressure genuinely does need dividing by 100, so it survived the mistake. The giveaway was arithmetic: 0.3 × 100 = 30 °C and 0.07 × 1024 ≈ 72 %RH, both entirely believable for a Chennai evening.
Step 02
02the board

Turning a reading into a web reply

The STM32 runs three stages in order, and the split matters because each stage has a different audience.

Stage 1

Sensor

Initialise the BME280 over I2C, take a first reading, print it to the serial console.

Stage 2

Bridge

Type AT commands in PuTTY; they travel through the STM32 to the Wemos and back. This is how the radio gets configured.

Stage 3

Responder

Listen for the Wemos forwarding a browser request, build a complete HTTP reply, send it back.

The board is not a web server in the usual sense — it has no IP address and no network stack. It is the application sitting behind the Wemos’s socket, writing the bytes of an HTTP response by hand:

main.c — the reply the browser receives221 bytes
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 74
Connection: close

{"status":"success","temperature":29.69,"humidity":74.93,"pressure":1008.35}

Every reply is timed. The console prints one line per request, and that line is the evidence for the 33 ms figure quoted at the top of this page:

PuTTY — one line per requestlive
[HTTP] link 0, 221 bytes, 33 ms, SEND OK
[HTTP] link 0, 221 bytes, 34 ms, SEND OK
The bug that made it take minutes. The first version polled the serial port one byte at a time and echoed each byte to PuTTY before reading the next. A browser sends 400–600 bytes of headers in a burst; at 115200 baud a byte arrives every 87 µs, and the echo cost about the same. Bytes were silently lost, the request never completed, and the browser waited. The fix was an interrupt-driven ring buffer, so nothing is ever missed regardless of what the rest of the program is doing.
Step 03
03the radio

Teaching a microcontroller to speak Wi-Fi

The Wemos D1 Mini runs AT firmware: it takes plain-text commands on the serial line and does the network work. Five of them are all the project needs.

CommandWhat it doesWhy it is needed
AT+CWMODE=1Station modeThe module joins a router rather than becoming one
AT+CWJAP="ssid","pass"Join the access pointGets the board an IP address
AT+CIFSRPrint the addressThis is the IP you type into Node-RED
AT+CIPMUX=1Allow several socketsMandatory before a server can start
AT+CIPSERVER=1,80Open a TCP server on port 80Makes the board reachable as a web page

Once the server is up, the traffic in both directions is plain text on the serial line. A browser request arrives wrapped in a prefix that says how many bytes follow; the reply is pushed back through a send window:

What actually crosses the serial linkUSART1 · 115200
in  → +IPD,0,78:GET / HTTP/1.1
      Host: 10.31.2.180

out ← AT+CIPSEND=0,221
      (module answers  >  )
      HTTP/1.1 200 OK ... {json body}
      (module answers  SEND OK )
The honest limitation. The Wemos remembers its Wi-Fi password across a reset but forgets CIPSERVER. Power-cycle it and it comes back joined to the network with port 80 closed — the board looks alive and answers pings while refusing every request. The fix is to re-issue the two commands on every boot, and to say so in the report rather than pretend it never happens. Campus Wi-Fi makes this worse: it usually uses WPA2-Enterprise with a username, which the AT firmware cannot do at all, so a phone hotspot is the reliable choice.
Step 04
04node-red

Where the numbers become information

Node-RED polls the board and receives a small JSON document. That document is the entire contract between the firmware and the dashboard — three numbers and a status word, so the software can tell a real reading from a failed one.

The JSON contractHTTP body
{ "status": "success",
  "temperature": 29.69,
  "humidity": 74.93,
  "pressure": 1008.35 }

A function node splits that object into separate messages, one per widget, so no chart ever has to understand JSON. Two flows run side by side: one polls the board every five seconds, the other asks OpenWeather every ten minutes.

Step 05

Four screens, four questions

Each dashboard answers one question and refuses to answer the others. That separation is deliberate: mixing a live reading with a ten-minute-old forecast on the same gauge is how people end up trusting the wrong number.

Step 06
06the verdict

Why one number agrees and two never will

Comparing two weather sources naively produces a table of differences and no insight. The useful question is whether the two numbers are even measuring the same thing.

Pressure is the same measurand, once both are reduced to mean sea level. The sensor reports the pressure where it stands; the API reports what that pressure would be at sea level. The correction is the standard barometric reduction, and at 30 m it is worth about 3.6 hPa — enough to make a perfectly healthy sensor look broken.

Compare — the only piece of physics in the dashboardNode-RED
// reduce station pressure to sea level before comparing
const sea = (p, alt) => alt === 0 ? p
  : p * Math.pow(1 - 0.0065 * alt / 288.15, -5.255);

Temperature and humidity are not the same measurand. The API reports air temperature at two metres over open ground in shade; our sensor measures the air beside a running microcontroller. A five-degree gap is not an error, it is the correct answer to a different question — and the verdict table says so instead of printing a red number.

QuantityBME280OpenWeatherΔVerdict
Pressure (hPa, MSL)1012.031012.000.03AGREES
Temperature (°C)29.9424.855.09EXPECTED OFFSET
Humidity (%RH)73.9692.00−18.04EXPECTED OFFSET

The tolerance is deliberately tight only where it is justified: 0.05 % for pressure, because both sides measure the same quantity on the same datum. For the other two, the system only raises an alarm when the gap becomes physically implausible — beyond 10 °C or 40 %RH — which is the point where a real fault would be suspected.

Step 07
07the insight

From a comparison to a decision

“Is the morning good?” is a poor question, because good for what? The last screen scores four different activities and ranks them, so the user gets options instead of a verdict they have to argue with.

Everything is built on one number a person can understand: how close the air is to being full of water. The dew point is the temperature at which air can hold no more moisture, and it comes from temperature and humidity alone.

Dew point — Magnus-TetensScore 4 options
const g  = Math.log(h / 100) + (17.27 * t) / (237.7 + t);
const td = (237.7 * g) / (17.27 - g);
const spread = t - td;   // small spread → dew on the grass

Each activity then gets its own sensitivity curve, because each one feels the weather differently. The marks out of 100 are plain arithmetic, not a black box:

ActivityTemperatureHumidityPressure
Dew photographymust sit close to the dew pointhigh humidity is the whole pointfalling pressure means rain, no dry leaves
Run or cycle20–25 °C ideal, above 30 °C costlyabove 70 % sweat stops evaporatingfalling pressure means a wet run
Outdoor yogacomfortable from 22–30 °Conly sticky above 85 %mild penalty

What the scores are and are not. The structure is defensible: each activity has a different physical sensitivity, and every score can be recomputed by hand from the printed values. The constants — six marks per degree for running, four for yoga — are engineering judgement tuned for Chennai, not fitted from data. Saying that out loud is more honest than claiming a calibration nobody performed.
What broke, and what it taught

Four failures worth more than the working version

Failure 01 · latency

Bytes were vanishing

Echoing each received byte to the serial console before reading the next one overran the single-byte receive register. A 600-byte request arrived as a fraction of itself. Fixed with an interrupt-driven ring buffer, which took the reply time from minutes to 33 ms.

Failure 02 · units

The sensor lied convincingly

0.30 °C and 0.07 %RH looked like a dead sensor. It was a unit mismatch: the driver returned degrees and we divided by 100 again. The pressure survived the bug because it genuinely needed dividing — which is exactly why it was the clue.

Failure 03 · state

The radio forgot its job

The ESP8266 keeps Wi-Fi credentials across a reset but not the TCP server setting, so a power blip left a board that answered pings and refused every request. Now the setup sequence is re-issued on every boot.

Failure 04 · tooling

Two dashboards, one port

Two Node-RED dashboard packages installed together fought over the same socket, and two pages claiming the same URL made the whole dashboard refuse to render. Deleting the duplicate fixed a problem that looked like broken code.

None of these were solved by reading documentation. All of them were solved by measuring something and being surprised by the answer.
